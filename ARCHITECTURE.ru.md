# Tellurium Engine — Структура архитектуры (концепция, без кода)

## 1. Высокоуровневая концепция

Tellurium — гибридный игровой движок для сложных 3D и средних 2D игр. Ядро построено на **Rust** (безопасность, логика, память, ECS, скрипты, ресурсы). Те части, где нужна максимальная производительность или готовые C++ библиотеки (графический конвейер DirectX 12 / Vulkan, физика PhysX / Bullet), вынесены в **C++ модуль**. Связка между языками реализуется через библиотеку **cxx** — статические, типизированные привязки с нулевым оверхедом и без сырых небезопасных указателей через границу.

Скриптовая основа — **Luau** (диалект Lua с типами, быстрым байт-кодом и безопасной песочницей), а не чистый Lua.

---

## 2. Слои архитектуры (снизу вверх)

| Уровень | Компонент | Язык | Ответственность |
|---|---|---|---|
| 0 | Платформа и ОС | Rust (абстракция) | Окно, ввод, файловая система, потоки, время |
| 1 | Rust ядро | Rust | Память, Luau рантайм, ECS, ресурсы, безопасность, шина событий |
| 2 | C++ графика и библиотеки | C++ | Render API (DX12 / Vulkan), PhysX / Bullet, шейдеры, материалы |
| 3 | Скриптовый уровень | Luau | Игровая логика, поведение сущностей, реакция на события |
| 4 | Редактор и UI | Rust + GUI | Unity-подобный интерфейс (проще): иерархия, инспектор, проект, сцена, консоль |

Зависимости идут строго снизу вверх. Нижний уровень не знает о верхнем.

## 3. Rust-ядро (фундамент)

### 3.1 Управление памятью
- Вся игровая логика и объекты движка живут под управлением Rust ownership / borrowing. Длинные生命周期 и доступ проверяются компилятором.
- ECS-сущности и компоненты размещаются в типовых аренах и пулах, чтобы избежать фрагментации кучи и garantirровать линейный обход в системах.
- Luau выделяет память внутри собственного состояния (`lua_State`). Из Rust к Luau обращаются через дескрипторы и идентификаторы, а не через сырые указатели.
- Передача данных в C++ только через `cxx::UniquePtr` / `cxx::SharedPtr` с явно ограниченным сроком жизни. Сырые указатели Rust-объектов не проходят сквозь cxx границу.

### 3.2 Luau рантайм
- Одна глобальная Luau VM на движок. Изоляция скриптов достигается легковесными потоками (coroutines / threads) внутри этой одной VM, а не созданием тяжелых и独立 `lua_State`. Это гарантирует работу общей шины событий и единого API для всех скриптов.
- Все скрипты выполняются в главном потоке ядра (main thread), чтобы избежать гонок данных в Luau VM.
- Регистрируется движковый API: доступ к ECS, ресурсам, событиям, времени, входу, трансформации. Вызов возможен только через безопасные Rust-обёртки.
- **Песочница скриптов:** Luau не имеет прямого доступа к файловой системе, сети или памяти за пределами своего состояния. Все запросы проходят через движковый API с проверкой прав.
- Квоты: лимиты CPU-времени и памяти на один скрипт, чтобы один плохой скрипт не «повесил» движок.
- Связь Luau → Rust: обработчики событий, сигналы, функции обратного вызова.
- Связь Rust → Luau: системы ECS могут вызывать скриптовые функции (`on_update`, `on_collision`, `on_start` и т.д.).

### 3.3 ECS (Entity Component System)
- **Сущность (Entity)** — лишь идентификатор (`EntityId`), без собственных данных.
- **Компоненты** — простые структуры данных (POD-подобные), хранятся в массивных хранилищах по типам.
- **Системы** — Rust-функции, которые обходят запросы (queries) по набору компонентов и изменяют данные.
- **Мир (World)** — центральный контейнер всех сущностей, компонентов и систем.
- **Скриптовый компонент (`ScriptComponent`)** — привязывает сущность к Luau скрипту и хранит дескриптор состояния скрипта.
- **События ECS** — отдельная шина сообщений: столкновения, триггеры, ввод, события жизненного цикла сущности.

### 3.4 Загрузка ресурсов (Resource Manager)
- Поддерживаемые ассеты: текстуры, меши/модели, шейдеры, материалы, аудио, сцены, Luau-скрипты.
- Кэширование по путям, подсчёт ссылок, асинхронная загрузка в отдельном потоке, чтобы не блокировать игровой цикл.
- **Импортер ресурсов** преобразует исходные файлы (`.fbx`, `.obj`, `.png`, `.wav`, `.luau` и т.д.) во внутренний оптимизированный формат движка.
- Ресурсы доступны через безопасные дескрипторы (`Handle<Texture>`, `Handle<Mesh>`, `Handle<AudioClip>`), а не через прямые пути к файлам.

### 3.5 Безопасность и защита
- **Безопасный Rust:** вся логика движка пишется в `safe Rust`. Блоки `unsafe` допускаются только в минимальных местах FFI-границ и должны быть обёрнуты в безопасные абстракции.
- **Граница cxx:** все переходы Rust → C++ типизированы библиотекой `cxx`; неявных приведений и неконтролируемого доступа к памяти нет.
- **Изоляция Luau:** скрипт не может вызвать системный API напрямую. Все операции с файлами, сетью, устройствами ввода проходят через движковый шлюз с проверкой прав.
- **Проверка указателей на границе:** C++ не сохраняет сырые указатели на объекты Rust; взаимодействие происходит через идентификаторы, дескрипторы или `cxx::SharedPtr`.

## 4. C++ модуль (графика и внешние библиотеки)

### 4.1 Графический абстракционный слой (Render Abstraction)
- Единый безопасный интерфейс на стороне Rust: `RenderDevice`, `RenderContext`, `SwapChain`, `Material`, `Texture`, `Mesh`.
- Бэкенды выбираются при инициализации: **DirectX 12** (Windows) или **Vulkan** (кроссплатформа).
- Конвейер рендеринга: вершинный и пиксельный шейдеры, константные буферы, текстуры, материалы, рендер-цели, буфер глубины/трафарета.
- Rust готовит список команд рендеринга (что нарисовать, с какими материалами, какая камера), C++ исполняет эти команды на GPU.

### 4.2 Физика
- Готовый физический движок на C++ (PhysX или Bullet) инкапсулируется в обёртку.
- ECS-система физики на Rust передаёт позиции, коллайдеры и параметры тел в C++ физику.
- События столкновений возвращаются из C++ в Rust через cxx и публикуются в шину событий ECS.
- Физические компоненты (`Rigidbody`, `Collider`) хранятся в Rust ECS; соответствующие физические тела — в C++, связаны по идентификатору сущности.

### 4.3 Модуль связки cxx (граница Rust ↔ C++)
- Описываются общие типы: `Vertex`, `Transform`, `AABB`, `MaterialData`, `TextureHandle`, `MeshHandle`.
- Функции моста: инициализация устройства, отрисовка кадра, загрузка текстуры, создание меша, шаг физики, рейкаст.
- Строки передаются через типизированные `&CxxString` / `&str`; числа и структуры — по значению или через умные указатели cxx.

## 5. Взаимодействие компонентов (схема данных)

```
Luau скрипт (компонент сущности)
        │
        ▼
Rust API (безопасный шлюз) ◄──────────────────┐
        │                                      │
        ▼                                      │
ECS / Мир / Системы                            │
        │                                      │
        ▼                                      │
Менеджер ресурсов                              │
        │                                      │
        ▼                                      │
cxx мост (типизированные привязки)             │
        │                                      │
        ├────────► C++ Render API ─────► GPU   │
        │                                      │
        └────────► C++ Физика (PhysX/Bullet)   │
```

Поток управления за кадр:
1. Ввод пользователя собирается на платформенном уровне (Rust).
2. Системы ECS и Luau-скрипты обновляют логику и трансформации.
3. Физика шагает в C++; результаты возвращаются в Rust.
4. Rust формирует команды рендеринга и передаёт их в C++ графику.
5. C++ отрисовывает кадр на GPU и выводит в окно.

## 6. Слой скриптов Luau

- Каждый Luau-скрипт — это компонент сущности (`ScriptComponent`).
- Доступный API из Luau: `entity`, `transform`, `components`, `resources`, `events`, `time`, `input`.
- Жизненный цикл скрипта: `on_start`, `on_update`, `on_fixed_update`, `on_collision`, `on_trigger`, `on_destroy`.
- Поддерживается типизация Luau (по желанию) для подсказок в редакторе и ранней проверки ошибок.
- Скрипт не может напрямую manipulatь память GPU или файловую систему; только через движковые дескрипторы.

## 7. Сцены и узлы (Godot-подобная иерархия)

### 7.1 Формат сцены `.telsc`
- Сцены хранятся в собственном формате движка с расширением **`.telsc`**.
- Формат может быть текстовым (удобно для версионного контроля) или бинарным (быстрая загрузка), выбирается в настройках проекта.
- В `.telsc` сохраняется дерево узлов, свойства компонентов, ссылки на ресурсы, прикреплённые Luau-скрипты и настройки сцены.

### 7.2 Узлы (Nodes) — как в Godot
- Каждый объект в сцене — это **узел (Node)**. Узел имеет имя, трансформацию, список компонентов и может иметь дочерние узлы.
- Узлы образуют древовидную иерархию сцены. Родительские трансформации наследуются дочерними.
- Типы корневых узлов: `Node2D`, `Node3D`, `Camera`, `Light`, `MeshInstance`, `Sprite`, `AudioStreamPlayer` и др.
- У узла может быть скриптовый компонент Luau, прикреплённый как поведение узла.

### 7.3 Связь узлов и ECS
- При загрузке `.telsc` движок создаёт ECS-сущности для узлов и компоненты для их данных.
- Transform узла хранится как компонент `Transform` в ECS.
- Скриптовые узлы получают компонент `ScriptComponent` с привязкой к Luau.
- Изменения в иерархии узлов в редакторе отражаются в ECS-мире сцены.

### 7.4 Инстансирование сцен
- Сцена может быть упакована как ресурс (PackedScene) и инстанциирована в другой сцене несколько раз.
- Каждый инстанс получает свой корневой узел и независимую копию дерева узлов.

## 8. Менеджер проектов (как в Godot)

### 8.1 Окно менеджера проектов
Перед открытием редактора запускается **менеджер проектов** — стартовое окно Tellurium, аналогичное Godot.

### 8.2 Доступные действия
- **Выбрать проект** — открыть существующий проект из списка.
- **Почитать о проекте** — просмотреть описание проекта, версию движка, путь к папке, дату последнего открытия.
- **Создать проект** — ввести имя, выбрать папку, шаблон (2D / 3D / пустой), создать структуру каталогов и файл проекта.
- **Сканировать проект** — указать папку на диске; движок ищет файлы проекта (например, `.tprj` или `project.toml`) и добавляет их в список.
- **Удалить проект** — удалить запись из менеджера (опционально — с удалением файлов проекта с диска после подтверждения).
- **Открыть проект** — загрузить проект и перейти в редактор.
- **Экспорт (Export/Build)** — выбор целевой папки на Windows, настройка параметров билда (Debug/Release, иконка приложения, включение консоли отладки) и запуск пайплайна сборки финального приложения.

### 8.3 Файл проекта
- Проект описывается конфигурационным файлом (например, `project.tprj` или `project.toml`).
- Содержит: имя проекта, версию Tellurium, графический бэкенд (DX12/Vulkan), пути к ассетам и сценам, список последних сцен, настройки редактора.

## 9. Пайплайн ассетов (Asset Pipeline) и импорт ресурсов

### 9.1 Скрытый процесс импорта
Когда пользователь добавляет исходный файл (`.png`, `.fbx`, `.wav`, `.luau`) в папку проекта через Проводник или окно Project, движок не использует его напрямую в рантайме. Менеджер ресурсов запускает фоновый пайплайн импорта.

### 9.2 Мета-файлы (`.telmeta`)
- Для каждого исходного ассета движок автоматически создает сопутствующий текстовый файл конфигурации с расширением `.telmeta` (например, `texture.png.telmeta`).
- В мета-файле хранятся: уникальный глобальный идентификатор ресурса (GUID), настройки импорта (тип фильтрации текстуры, компрессия звука) и хэш версии файла для отслеживания изменений.
- Файлы `.telmeta` обязательны для систем контроля версий (Git), так как гарантируют, что у всех разработчиков в команде ассеты настроены одинаково.

### 9.3 Кэш ассетов (`.telcache`)
- Результат работы импортера сохраняется в скрытую системную директорию `.telcache/` внутри проекта.
- Пайплайн преобразует тяжелые исходники в оптимизированные для GPU и CPU бинарные форматы Tellurium (например, `.png` пережимается в текстурный формат со сжатием BC7/ASTC, а `.fbx` — в плоский массив вершин с готовыми индексными буферами).
- В рантайме и в режиме игры редактор загружает данные исключительно из `.telcache`, используя безопасные дескрипторы `Handle<T>`.

### 9.4 Сборка финального билда (Baking)
При экспорте готовой игры на целевую платформу система сборки упаковывает содержимое `.telcache` и файлы конфигурации проекта в монолитные бинарные архивы (`.telpak`), полностью отсекая исходные файлы и код самого редактора.

## 10. Редактор и пользовательский интерфейс (Unity 2022-подобный, но проще)

Окно редактора разделяется на визуальные зоны:

- **Hierarchy (Иерархия)** — дерево узлов текущей сцены со списком компонентов на каждом узле.
- **Inspector (Инспектор)** — свойства выбранного узла и его компонентов, включая прикреплённые Luau-скрипты и их поля.
- **Project (Проект)** — окно ассетов: папки ресурсов, текстуры, модели, скрипты, материалы.
- **Scene View (Сцена)** — визуальное представление сцены в редакторе (3D или 2D), камера редактора, выделение объектов.
- **Game View (Игра)** — окно запуска игры со встроенным рендером, отображает то, что увидит игрок.
- **Console (Консоль)** — логи движка, ошибки Luau, предупреждения безопасности и FFI.
- **Toolbar (Панель инструментов)** — Play / Pause / Step, настройки сборки, выбор графического бэкенда, профили, кнопка «Export Project» (экспорт финального приложения для Windows).

Принципы интерфейса: меньше вложенных меню, больше визуальных блоков, контекстные панели appear при выделении объекта, единая цветовая тема и сетка, чёткое выравнивание элементов.

## 12. Жизненный цикл кадра (Game Loop)

1. **Input** — сбор событий ввода (клавиатура, мышь, геймпад, тач).
2. **Pre-update** — системы подготовки, вызов `on_start` для новых скриптов.
3. **ECS update** — системы игровой логики; вызов Luau `on_update` для скриптовых компонентов. Запуск/планирование параллельного шага физики (Fixed Update) в отдельном потоке.
4. **Physics step (синхронизация)** — не блокирующий шаг симуляции в главном потоке. Чтение последних готовых трансформаций из параллельного физического потока через двойную буферизацию и запись их в ECS-компоненты `Transform`. Новый шаг физики запускается асинхронно для следующего кадра.
5. **Render preparation** — сборка камер, источников света, материалов, видимых объектов.
6. **Render draw** — команды рендеринга передаются через cxx в C++ графику и исполняются на GPU.
7. **Present** — замена front/back буферов, вывод кадра на экран.
8. **Post-frame** — очистка временных ресурсов, публикация событий конца кадра, подготовка к следующему кадру.

## 13. Логическая структура каталогов (без кода)

```
tellurium/
├── core/             # Rust ядро: память, мир ECS, системы, события, безопасность
├── scripting/        # Luau рантайм, привязка движкового API, скриптовый компонент
├── assets/           # Менеджер ресурсов, импорт ассетов, кэш, дескрипторы
├── safety/           # Политики безопасности, sandbox скриптов, аудит FFI-границ
├── bridge/           # cxx модуль: описание общих типов и функций границы Rust ↔ C++
├── graphics-cpp/     # C++ графика: бэкенды DX12 / Vulkan, шейдеры, материалы
├── physics-cpp/      # C++ физика: обёртка PhysX / Bullet
├── editor/           # Редактор: UI, окна, иерархия, инспектор, проект, консоль, менеджер проектов
├── platform/         # Абстракция окна, ввода, файловой системы, потоков
├── runtime/          # Точка входа, игровой цикл, управление сценами
├── builder/          # Пайплайн упаковки .telpak и сборки релиза (экспорт проекта)
└── templates/windows/# Предкомпилированный шаблон рантайма tellurium_runtime.exe для Windows
```

## 14. Зависимости (текстовая схема)

```
Editor → Scripting → Core → Platform
                    ↑           │
                    │           ▼
                cxx мост → Graphics-CPP → DX12 / Vulkan → GPU
                    │
                    ▼
                Physics-CPP → PhysX / Bullet
```

- `Scripting` зависит от `Core` и `Luau`.
- `Core` зависит от `Platform`.
- `Graphics-CPP` и `Physics-CPP` доступны только через `cxx` мост из `Core`.
- Никакой прямой зависимости C++ кода от Luau или внутренних структур Rust.

## 15. Этапы развития (кратко)

1. **Ядро:** Rust, ECS, Luau runtime, базовое окно и ввод.
2. **Мостик и графика:** cxx границы, базовый рендер (очистка экрана, треугольник).
3. **Ресурсы:** загрузка текстур, мешей, шейдеров, материалов.
4. **Физика:** подключение PhysX / Bullet через C++, события столкновений в ECS.
5. **Редактор:** менеджер проектов, Hierarchy, Inspector, Project, Scene View, Game View, Console.
6. **Полировка:** полный цикл кадра, оптимизация, песочница скриптов, документация API.

## 16. Принципы «аккуратности»

- Чёткое разделение ответственности: **Rust — логика, безопасность, память, скрипты; C++ — производительность GPU и готовые внешние библиотеки.**
- Единый стиль именования модулей, компонентов и систем.
- Граница `cxx` обозначена явно; все публичные API задокументированы.
- Интерфейс редактора консистентен: одна тема (палитра Tellurium), выравнивание по сетке, контекстные подсказки, одинаковое поведение выделения и свойств.

## 17. Архитектурные вызовы и решения

### 17.1 Двойное владение (Double Ownership) в физике и рендере

**Проблема:** Компоненты (`Rigidbody`, `Collider`, `Transform`) лежат в Rust ECS, а физические тела живут внутри C++ (PhysX / Bullet). Аналогично — меши и текстуры: дескрипторы в Rust, данные на GPU в C++. Если сущность в ECS удаляется, но не синхронизировать удаление с C++, в физическом мире останется «призрачное» тело, которое будет продолжать сталкиваться с объектами.

**Решение:**
- Система событий жизненного цикла ECS. При удалении `RigidbodyComponent` или `ColliderComponent` в Rust, система отправляет команду через cxx мост на удаление соответствующего объекта из физического мира C++.
- Удаление компонента в Rust считается «источником истины» (source of truth); C++ физика не удаляет тела по своей инициативе, только по команде из Rust.
- Для рендеринга: при удалении компонента `MeshRenderer` в Rust, команда на освобождение меша/материала на GPU отправляется в C++ рендер.
- Каждый объект в C++ хранит идентификатор сущности ECS (`EntityId`), чтобы при очистке можно было свериться с живыми сущностями.

### 17.2 Передача команд рендеринга (Render Command Buffer)

**Проблема:** Если на каждом кадре гонять трансформации тысяч объектов из Rust в C++ по одному через отдельные cxx-функции, производительность упрётся в накладные расходы на FFI-вызовы, даже несмотря на нулевой оверхед cxx.

**Решение:**
- На этапе **Render preparation** (шаг 5 жизненного цикла кадра) Rust сформирует один линейный массив (буфер) сырых данных: ID меша, ID материала, матрица трансформации, флаги видимости.
- Этот массив передаётся в C++ **одним вызовом** в виде среза данных `&[RenderCommand]`.
- C++ модуль за один проход забивает командные буферы DirectX 12 / Vulkan и отправляет их на GPU.
- Для частых обновлений (трансформации) используется буфер констант (constant buffer / uniform buffer), который обновляется блочно, а не по объекту.

### 17.3 Потоковая модель (Multithreading)

**Проблема:** Жизненный цикл кадра изначально описан строго последовательно. Современные движки распараллеливают физику и логику.

**Решение (закладывается на этапе концепта):**
- **ECS update (Rust)** и **Physics step (C++)** могут работать параллельно, если используется разделение на `Update` и `Fixed Update`.
- Физика считается в своём фиксированном тайминге в отдельном потоке.
- Графический кадр просто интерполирует последние полученные из C++ трансформации (интерполяция между кадрами физики для плавности).
- Синхронизация между потоками осуществляется через двойную буферизацию трансформаций: один буфер пишется физикой, другой читается рендером, затем они меняются местами.
- **Luau-скрипты выполняются строго в главном потоке ядра (main thread).** Изоляция скриптов достигается за счет легковесных корутин внутри одной Luau VM, а не созданием отдельных `lua_State`, чтобы не ломать общую шину событий и единое API.

### 17.4 Кросс-языковой сборщик мусора (Cross-Language GC)

**Проблема:** В движке сосуществуют три разные модели управления памятью: строгий Ownership/Borrowing в Rust, автоматический Garbage Collector (GC) в Luau и ручное/умное управление (умные указатели C++) в графическом/физическом модулях. Возникает риск циклической зависимости: Luau держит ссылку на Rust-объект, который связан с C++ ресурсом, и память никогда не освобождается.

**Решение:**
- Использование "слабых" дескрипторов (Weak Handles / EntityId) на стороне Luau вместо хранения прямых ссылок на ресурсы.
- Жизненным циклом тяжелых объектов (меши, текстуры, физические тела) полностью управляет Rust ECS и Менеджер ресурсов.
- Когда в Luau срабатывает цикл сборки мусора и уничтожается скриптовый компонент, он не удаляет память сам, а отправляет событие в Rust Event Bus. Rust на следующем кадре безопасно деаллоцирует объект ядра и шлет команду на очистку в C++.

### 17.5 Детерминизм шины событий (Event Bus Bottleneck)

**Проблема:** При высокой плотности объектов (например, тысячи пуль или частиц, генерирующих события столкновения) шина событий Event Bus может стать «узким горлышком» (bottleneck) и переполнить память, замедляя кадр.

**Решение:**
- Разделение шины на **Немедленные события** (Immediate Events, обрабатываются жестко внутри систем в текущем кадре, например, триггеры физики) и **Отложенные события** (Deferred Events, буферизируются и разгребаются на следующем кадре).
- Введение механизма фильтрации событий на стороне C++ (продюсера): если Luau-скрипт не подписан на коллизии конкретного объекта, C++ модуль физики даже не генерирует и не отправляет это событие через cxx-мост, экономя такты процессора.

## 19. Система горячей перезагрузки (Hot Reloading)

### 19.1 Отслеживание изменений ресурсов (Resource Manager)

Менеджер ресурсов на Rust подписывается на системные уведомления ОС (вкладка файловой системы, watcher) за изменениями следующих типов файлов:

- `.luau` — исходный код скриптов.
- `.png` и другие форматы текстур.
- `.telsc` — файлы сцен.

При изменении любого из этих файлов Resource Manager получает событие от ОС, помечает соответствующий ресурс как «требует перезагрузки» и ставит его в очередь на горячую перезагрузку. Очередь обрабатывается в начале следующего кадра, чтобы не прерывать текущий рендер и не создавать гонок данных между потоками.

### 19.2 Бесшовная перезагрузка Luau-скриптов (State Preserving)

Когда Luau-скрипт меняется на диске:

1. Resource Manager уведомляет Scripting модуль о изменении конкретного `.luau` файла.
2. Scripting компилирует новую версию скрипта в отдельном байт-коде, не останавливая текущую Luau VM.
3. Для каждого `ScriptComponent`, использующего этот скрипт, выполняется замена реализации функций (`on_start`, `on_update`, `on_collision` и т.д.) на новые.
4. **State Preserving:** текущее состояние переменных скрипта (поля компонента, значения свойств) сохраняется. Игра не сбрасывается, сущности не пересоздаются, позиция и настройки узлов остаются прежними. Меняется только логика поведения.

Если в новом скрипте появились новые поля или изменились существующие, Инспектор редактора автоматически подхватывает изменения и отображает их без перезапуска редактора.

### 19.3 Горячая перезагрузка текстур и шейдеров (C++ Render)

Для ресурсов, которые живут на GPU (текстуры, шейдеры, материалы):

1. Resource Manager загружает обновлённые данные файла (`.png`, `.hlsl`, `.glsl` и т.д.) в Rust.
2. Через cxx мост отправляется команда в C++ графический модуль: обновить текстуру или перекомпилировать шейдер.
3. C++ модуль загружает новые данные в существующие GPU-ресурсы (т.е. не создаёт новый конвейер, не пересоздаёт устройство, не пересоздаёт swap chain).
4. Текстура замещается на лету, шейдер перекомпилируется и привязывается к материалу. Все объекты, использующие этот материал, мгновенно отображают обновлённый вид.

Графический конвейер продолжает работать без перезапуска. Активный рендер не прерывается, видимый кадр не моргает.

## 20. Архитектура плагинов и расширений редактора

### 20.1 Расширяемость интерфейса редактора

Сторонние разработчики могут создавать кастомные окна, вкладки и инструменты для редактора Tellurium, используя встроенную UI-систему движка:

- Плагин может зарегистрировать новую вкладку в главном рабочем окне (рядом с Hierarchy, Inspector, Project).
- Плагин может создать плавающее окно с собственным содержимым (например, визуальный скриптогенератор, редактор анимаций, окно профилировщика).
- Плагин может добавить пункты в контекстные меню, кнопки на Toolbar, элементы в Инспектор для кастомных компонентов.
- Элементы плагина используют тёплую тёмную палитру редактора из §11.

### 20.2 Два типа плагинов

**Rust-плагины (глубокая интеграция):**
- Реализуются как динамические библиотеки (`.dll` на Windows, `.so` на Linux).
- Имеют полный доступ к ядру через cxx мост: к ECS, к Resource Manager, к Luau рантайму, к C++ графике и физике.
- Подходят для импортеров нестандартных форматов ассетов, кастомных систем рендеринга, интеграции с внешними сервисами.
- Загружаются редактором при старте и изолируются через отдельные точки входа; ошибка в Rust-плагине не должна падать ядро движка.

**Luau-плагины (безопасные скрипты):**
- Реализуются на Luau и запускаются внутри изолированного Luau-состояния редактора.
- Имеют ограниченный доступ: только через движковый API, без прямого доступа к файловой системе или сети.
- Подходят для автоматизации редактора, создания кастомных Инспекторов, скриптовой валидации сцен, générаторов узлов и прочих инструментов уровня редактора.
- Песочница Luau гарантирует, что плагин не может повредить состояние ядра или выполнить вредоносные операции.

### 20.3 Изоляция через шину событий (Event Bus)

Для стабильности редактора все взаимодействие плагинов с ядром и между собой идёт через шину событий:

- Плагин не вызывает функции ядра напрямую, а публикует события в Event Bus (например, `SceneOpened`, `EntitySelected`, `ResourceReloaded`).
- Ядро и другие плагины подписываются на события и реагируют на них асинхронно.
- Если плагин generates некорректное событие или падает при обработке, ядро перехватывает исключение на границе плагина и продолжает работу без перезапуска редактора.
- Event Bus работает как буфер обмена: плагин А не знает о существовании плагина Б, они обмениваются только сообщениями через шину.

Это гарантирует, что сторонние расширения не могут нарушить целостность сцены, зависания редактора или повреждения ресурсов.

## 21. Система экспорта проекта (Windows Build Pipeline)

### 21.1 Процесс сборки (Baking)

Сборка финального приложения Tellurium для Windows выполняется модулем **builder** (Rust) по следующему алгоритму:

1. **Валидация проекта** — проверяется наличие файла проекта (`.tprj` или `project.toml`), целостность ссылок на сцены и ассеты.
2. **Сборка байт-кода Luau** — все `.luau` скрипты проекта компилируются в байт-код Luau. Исходный код скриптов не включается в финальный билд.
3. **Упаковка ресурсов** — содержимое директории `.telcache/` (оптимизированные текстуры, меши, шейдеры, материалы, аудио, сцены `.telsc`) собирается в монолитный архив `.telpak`.
4. **Сборка конфигурации** — файл проекта (`.tprj` / `project.toml`) сериализуется и вкладывается в `.telpak` для использования рантаймом.
5. **Отсечение редактора** — исходный код редактора, исходные ассеты (`.png`, `.fbx`, `.wav`, `.luau`), мета-файлы (`.telmeta`) и код самого редактора полностью отсекаются и не попадают в финальный билд.
6. **Формирование исполняемого файла** — к предкомпилированному шаблону `tellurium_runtime.exe` привязывается (или размещается рядом) файл `.telpak`, после чего получается готовый к запуску `.exe`.

### 21.2 Упаковка данных (.telpak)

`.telpak` — монолитный бинарный архив, содержащий всё необходимое для запуска игры на целевой платформе:

| Содержимое | Источник | Назначение |
|---|---|---|
| Байт-код Luau | Компиляция `.luau` скриптов проекта | Игровая логика, поведение узлов |
| Оптимизированные ресурсы | `.telcache/` (текстуры, меши, шейдеры, материалы, аудио) | GPU- и CPU-готовые данные |
| Сцены | `.telsc` (упакованные из `.telcache`) | Иерархия узлов и сцены |
| Конфигурация проекта | `.tprj` / `project.toml` | Имя, бэкенд DX12/Vulkan, пути, настройки |

Архив形成ется на этапе **Упаковки ресурсов** и записывается как единый бинарный файл. В рантайме данные читаются из `.telpak` через безопасные дескрипторы `Handle<T>` без доступа к исходным файлам проекта.

### 21.3 Сборка исполняемого файла (.exe)

Финальный рантайм для Windows формируется следующим образом:

- Берется **предкомпилированный легковесный шаблон** `tellurium_runtime.exe` из директории `templates/windows/`.
- Шаблон инициализирует ядро Tellurium (Rust) и загружает C++ модуль через `cxx` мост — точно так же, как и в редакторе.
- Шаблон считывает привязанный или лежащий рядом файл `.telpak`, извлекает байт-код Luau, ресурсы и конфигурацию.
- Игра запускается без редактора, без исходного кода и без инструментов разработки.

### 21.4 Экспорт зависимостей

Для работы финального `.exe` на Windows подтягиваются необходимые динамические библиотеки:

- **d3d12.dll** или **Vulkan-лоадер** — в зависимости от выбранного графического бэкенда в настройках проекта.
- **PhysX / Bullet .dll** — если физическая библиотека не линкуется статически.
- Все зависимости копируются в папку с исполняемым файлом или линкуются статически по выбору в параметрах билда.

### 21.5 Разделение обязанностей

- **Rust (builder):** парсинг файлов проекта, компиляция Luau, упаковка `.telpak`, копирование зависимостей, формирование `.exe`. Работа с файловой системой и безопасность — полностью на Rust.
- **C++ модуль:** инициализируется в рантайме экспортированного билда через `cxx` мост, аналогично редактору. Графика и физика работают в финальном приложении без изменений.
- **cxx мост:** остается единственной границей между Rust и C++ в экспортированном билде.

## 22. Система сериализации и сохранений (Save/Load & Снапшоты)

В формате `.telsc` уже описан хранение сцен, но рантайму необходим чёткий механизм перевода сущностей из памяти в бинарный/текстовый формат и обратно прямо во время игры.

### 22.1 Сериализация компонентов

- Каждый ECS-компонент поддерживает автоматическое сохранение через Rust-библиотеку **serde**.
- Сериализация покрывает: Transform (позиция, поворот, масштаб), Rigidbody, Collider, MeshRenderer, ScriptComponent и пользовательские компоненты.
- Компоненты помечаются derive-ами `Serialize` / `Deserialize`, что позволяет преобразовывать их в бинарный или текстовый формат без ручного кода преобразования полей.
- ScriptComponent сериализуется вместе с привязкой к Luau-скрипту: сохраняется ссылка на скрипт (`EntityId` скрипта или путь к `.luau`) и текущие значения скриптовых переменных (состояние скрипта).

### 22.2 Снапшот Мира (World Snapshot)

- Возможность «заморозить» текущее состояние ECS-мира со всеми `EntityId`, позициями и переменными Luau-скриптов.
- Снапшот записывается в файл сохранения или передаётся по сети (для сетевой синхронизации / реплеев).
- Процесс снапшота:
  1. Обход всех сущностей в мире ECS.
  2. Сериализация каждого компонента через serde.
  3. Сохранение связей между сущностями (родитель -> дочерние узлы в иерархии сцены).
  4. Запись состояния Luau VM: активные корутины, значения переменных скриптов.
  5. Сборка в единый бинарный/текстовый файл сохранения (`.telsave`).
- Восстановление мира из снапшота выполняется в обратном порядке: десериализация компонентов, восстановление связей `EntityId`, пересоздание скриптовых компонентов с привязкой к Luau.

## 23. Подсистема аудио (Audio Engine)

Игра без звука — это просто симуляция. Аудио-движок связывает Rust ECS с C++ библиотекой низкоуровневого звука (например, miniaudio, FMOD или OpenAL).

### 23.1 Компоненты аудио

- **AudioSourceComponent** — излучатель звука, прикреплённый к узлу/сущности. Хранит ссылку на аудиоклип (`.wav`, `.ogg` и др.), громкость, флаг зацикливания, режим 3D/2D.
- **AudioListenerComponent** — уши игрока, обычно прикреплённые к камере. Один активный Listener на сцену.

### 23.2 3D-звук

- Математический расчёт затухания звука на основе расстояния между Listener и Source.
- Панорамирование (левый/правый канал) в зависимости от относительного положения источника и слушателя.
- Доплеровский эффект — изменение частоты звука приrelative движении источника и слушателя.
- Все расчёты выполняются через **cxx мост**: Rust передаёт позиции Listener и Source в C++ аудио-библиотеку, которая возвращает итоговые параметры микширования.

### 23.3 Связи

- Часть: [[02 C++ модуль]] (аудио-библиотека на C++)
- Связано с: [[01.3 ECS]] (компоненты AudioSource, AudioListener)
- Связано с: [[02.3 cxx мост|cxx мост]] (передача позиций и параметров звука в C++)

## 26. Системы ввода и контекстных действий (Enhanced Input System)

В разделе 12 («Жизненный цикл кадра») сбор ввода упомянут на шаге 1, но рантайму необходима гибкая архитектура обработки сигналов, которая изолирует низкоуровневые кнопки железа от логики Luau-скриптов. Серьезный движок не должен проверять «нажата ли клавиша Space» внутри скрипта игрока; он должен проверять абстрактное действие «Jump».

### 26.1 Карта контекстных действий (Input Action Mapping)

Вместо прямой привязки к хардверным клавишам вводится слой абстракции: **Actions** (Действия).

Действия делятся на три типа:

1. **Digital (Триггерные)** — дискретные действия (Вкл/Выкл), например: Jump, Interact, Shoot.
2. **Analog / Axis (Осевые)** — одномерные или двумерные значения, например: Move как Vector2, Look для мыши, Throttle для курков геймпада.
3. **Pass-through (Сквозные)** — сырые данные, например: координаты клика мыши, текстовый ввод.

Конфигурация привязок хранится в файле проекта (`project.toml`) и настраивается в редакторе (выбор клавиш клавиатуры, осей мыши или геймпада под конкретное действие).

### 26.2 Контексты ввода (Input Contexts)

Возможность динамически переключать наборы активных действий во время игры.

- Пример: при открытии инвентаря контекст `GameplayContext` (где работают оси движения и кнопка стрельбы) временно отключается, а активируется `UIContext` (где те же кнопки геймпада отвечают за навигацию по ячейкам).
- **Приоритеты контекстов** предотвращают ситуацию, когда нажатие кнопки «Esc» одновременно закрывает меню игры и ставит саму игру на паузу.

### 26.3 Архитектурный мост (Platform ↔ Core ↔ Luau)

1. **Модуль platform (Rust)** собирает сырые прерывания ОС Windows (события оконной петли Win32 / GLFW).
2. **Модуль core** транслирует сырые скан-коды клавиш в активные Actions на основе текущего контекста и публикует их в шину событий Event Bus.
3. **Luau-скрипты** подписываются не на клавиши, а на события действий. API из Luau выглядит как безопасный коллбэк: `input.bind_action("Jump", on_jump)`.

### 26.4 Связи

- Часть: [[Платформа]] (низкоуровневые события ОС)
- Связано с: [[01 Rust Ядро]] (генерация событий на основе карты действий)
- Связано с: [[Event Bus]] (распространение сигналов ввода до систем)
- Используется в: [[01.2 Luau рантайм]] (доступ скриптов к обработке высокоуровневых действий игрока)

```
tellurium/
├── core/             # Rust ядро: память, мир ECS, системы, события, безопасность

├── graphics-cpp/     # C++ графика: бэкенды DX12 / Vulkan, шейдеры, материалы
├── physics-cpp/      # C++ физика: обёртка PhysX / Bullet
├── audio-cpp/        # C++ аудио: miniaudio / FMOD / OpenAL, 3D-звук
├── input/            # Система ввода: карты действий (Action Mapping), контексты, обработка осей
├── serialization/    # Система сохранений, serde, снапшоты мира
├── diagnostics/      # Инструменты отладки и профилирования (Tracy, консоль)
├── editor/           # Редактор: UI, окна, иерархия, инспектор, проект, консоль, менеджер проектов
├── platform/         # Абстракция окна, ввода, файловой системы, потоков
├── runtime/          # Точка входа, игровой цикл, управление сценами
├── builder/          # Пайплайн упаковки .telpak и сборки релиза (экспорт проекта)
└── templates/windows/# Предкомпилированный шаблон рантайма tellurium_runtime.exe для Windows
```

## 28. Этапы развития (кратко)

1. **Ядро:** Rust, ECS, Luau runtime, базовое окно и ввод.
2. **Мостик и графика:** cxx границы, базовый рендер (очистка экрана, треугольник).
3. **Ресурсы:** загрузка текстур, мешей, шейдеров, материалов.
4. **Физика:** подключение PhysX / Bullet через C++, события столкновений в ECS.
5. **Редактор:** менеджер проектов, Hierarchy, Inspector, Project, Scene View, Game View, Console.
6. **Полировка:** полный цикл кадра, оптимизация, песочница скриптов, документация API.
7. **Экспорт:** Windows Build Pipeline, .telpak, tellurium_runtime.exe.
8. **Ввод:** Enhanced Input System, контексты действий, карты привязок.
9. **Сохранения:** сериализация через serde, снапшоты мира.
10. **Аудио:** 3D-звук, AudioSource / AudioListener, cxx мост.
11. **Отладка:** Tracy профилировщик, метрики в Console.
