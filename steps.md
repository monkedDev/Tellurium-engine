# Tellurium Engine — этапы разработки первой версии

Источник архитектуры: `ARCHITECTURE.ru.md` и 그래ф модулей из папки `Tellurium/`.

Цель первых релизов: готовый игровой движок со всем перечисленным в архитектуре — от ядра и рендера до редактора, экспорта `.exe` и отладки.

---

## Модули, которые нужно реализовать (из графа Tellurium/)

```
tellurium/
├── core/             # Rust ядро: память, мир ECS, системы, события, безопасность
├── scripting/        # Luau рантайм, привязка движкового API, скриптовый компонент
├── assets/           # Менеджер ресурсов, импорт ассетов, кэш, дескрипторы
├── safety/           # Политики безопасности, sandbox скриптов, аудит FFI-границ
├── bridge/           # cxx модуль: описание общих типов и функций границы Rust ↔ C++
├── graphics-cpp/     # C++ графика: бэкенды DX12 / Vulkan, шейдеры, материалы
├── physics-cpp/      # C++ физика: обёртка PhysX / Bullet
├── audio-cpp/        # C++ аудио: miniaudio / FMOD / OpenAL, 3D-звук
├── input/            # Система ввода: карты действий (Action Mapping), контексты, обработка осей
├── serialization/    # Система сохранений, serde, снапшоты мира
├── diagnostics/      # Инструменты отладки и профилирования (Tracy, консоль)
├── editor/           # Редактор: UI, окна, иерархия, инспектор, проект, консоль, менеджер проектов
├── platform/         # Абстракция окна, ввода, файловой системы, потоков
├── runtime/          # Точка входа, игровой цикл, управление сценами
├── builder/          # Пайплайн упаковки .telpak и сборки релиза (экспорт проекта)
└── templates/windows/# Предкомпилированный шаблон рантайма tellurium_runtime.exe для Windows
```

## Шаг 1 — Фундамент: платформа, Rust-ядро, ECS, Luau рантайм, игровой цикл

**Модули:** `platform`, `core`, `scripting`, `runtime`  
**Ссылки в архитектуре:** §3 (Rust-ядро), §6 (Luau рантайм), §12 (Жизненный цикл кадра), §13 (структура каталогов), §14 (зависимости)

**Что кодить:**
1. `platform/` — создание окна, сбор сырых событий ввода (клавиатура, мышь, геймпад), файловая система, потоки, таймер/время, **структура `RawInputState` для накопления сырого ввода между кадрами** (буферизация, чтобы системы ввода и Luau могли читать события на шаге ECS update).
2. `core/` — ECS: `EntityId`, компоненты (POD-структуры), хранилища компонентов по типам, системы, мир `World`, шина событий `Event Bus`.
3. `scripting/` — одна глобальная Luau VM, регистрация движкового API (`entity`, `transform`, `components`, `resources`, `events`, `time`, `input`), компонент `ScriptComponent`, жизненный цикл скриптов (`on_start`, `on_update`, `on_fixed_update`, `on_collision`, `on_trigger`, `on_destroy`), песочница скриптов (нет прямого доступа к ФС/сети), **кастомный аллокатор Luau VM с лимитами памяти и CPU-квоты на один скрипт** (раздел 3.2 архитектуры — настраивается один раз при инициализации VM).
4. `runtime/` — точка входа, игровой цикл: Input → Pre-update → ECS update → Physics step → Render preparation → Render draw → Present → Post-frame.

**Критерий завершения шага 1:** открывается пустое окно, работает игровой цикл, можно создать ECS-сущность, прикрепить Luau-скрипт, и из скрипта через безопасный API изменить данные сущности (например, позицию); сырой ввод буферизируется в `RawInputState` между кадрами; Luau VM запущена с кастомным аллокатором и квотами.

## Шаг 2 — Мостик и графика: cxx граница, C++ рендер (DX12 / Vulkan)

**Модули:** `bridge`, `graphics-cpp`  
**Ссылки в архитектуре:** §4.1 (Графический абстракционный слой), §4.2 (Физика — только cxx часть), §4.3 (cxx мост), §17.2 (Рендер-командный буфер), §21 (экспорт — для понимания, что графика должна работать и в финальном .exe)

**Что кодить:**
1. `bridge/` — типизированные общие типы (`Vertex`, `Transform`, `AABB`, `MaterialData`, `TextureHandle`, `MeshHandle`), функции моста (инициализация устройства, отрисовка кадра, загрузка текстуры, создание меша, шаг физики, рейкаст), строки через `&CxxString` / `&str`.
2. `graphics-cpp/` — `RenderDevice`, `RenderContext`, `SwapChain`, бэкенд DirectX 12 (Windows) или Vulkan, вершинный/пиксельный шейдеры, константные буферы, текстуры, материалы, рендер-цели, буфер глубины/трафарета.
3. Рендер-командный буфер: Rust собирает за кадр линейный массив `&[RenderCommand]` (ID меша, ID материала, матрица трансформации, флаги видимости) и передаёт его в C++ одним вызовом.

**Критерий завершения шага 2:** на экране отображается цветной треугольник (или цветная очистка экрана), рендеринг идёт через C++ графику, команда рендера формируется в Rust и исполняется на GPU.

## Шаг 3 — Ресурсы, физика, аудио, ввод

**Модули:** `assets`, `physics-cpp`, `audio-cpp`, `input`  
**Ссылки в архитектуре:** §3.4 (Менеджер ресурсов), §4.2 (Физика), §23 (Подсистема аудио), §26 (Системы ввода и контекстных действий), §9 (Пайплайн ассетов)

**Что кодить:**
1. `assets/` — менеджер ресурсов, дескрипторы `Handle<T>` (`Handle<Texture>`, `Handle<Mesh>`, `Handle<AudioClip>` и т.д.), кэширование по путям, подсчёт ссылок, асинхронная загрузка в отдельном потоке, импортер (`.png`, `.fbx`, `.wav`, **.ogg**, `.luau` → внутренний оптимизированный формат), `.telmeta`, `.telcache`.
2. `physics-cpp/` — **обёртка Bullet (фиксированный бэкенд, только CPU-версия)**, физические тела и коллайдеры, связаны с ECS по `EntityId`, шаг физики, рейкаст, события столкновений возвращаются в Rust через cxx и публикуются в Event Bus ECS.
3. `audio-cpp/` — аудио-библиотека (miniaudio / FMOD / OpenAL), компоненты `AudioSource` / `AudioListener`, 3D-затухание, панорамирование, доплеровский эффект, передача параметров через cxx мост.
4. `input/` — карта контекстных действий (Action Mapping): цифровые, аналоговые/осевые и сквозные действия, контексты ввода с приоритетами (GameplayContext vs UIContext), перевод сырых скан-кодов в абстрактные действия (`Jump`, `Move`, `Shoot`), API `input.bind_action("Jump", on_jump)` для Luau.

**Критерий завершения шага 3:** текстура и меш загружаются из `.telcache` и отрисовываются; физический объект падает и сталкивается с другим (событие приходит в Luau); играет 3D-звук (поддерживаются `.wav` и `.ogg`); нажатие кнопки вызывает абстрактное действие в скрипте.

## Шаг 4 — Сцены, узлы, сериализация, редактор

**Модули:** `editor`, `serialization`  
**Ссылки в архитектуре:** §7 (Сцены и узлы), §8 (Менеджер проектов), §9 (Пайплайн ассетов), §10 (Редактор и пользовательский интерфейс), §11 (Цветовая палитра интерфейса), §22 (Система сериализации и сохранений)

**Готовые иконки редактора.** Файлы находятся в [`assets/icons/`](assets/icons/) относительно корня проекта. SVG-пиктограммы 24×24 покрывают менеджер проектов, панели редактора, команды Play/Pause/Step/Stop и Export, сцены, узлы, компоненты, ассеты и консоль. Для окна редактора подготовлены `tellurium-editor.png` и `tellurium-editor.ico` (16–256 px).

**Что кодить:**
1. `serialization/` — serde-сериализация ECS-компонентов (Transform, Rigidbody, Collider, MeshRenderer, ScriptComponent и пользовательские), формат сцены `.telsc` (текстовый/бинарный), снапшоты мира (сохранение/загрузка `.telsave`), восстановление связей `EntityId`, состояние Luau-скриптов в снапшоте.
2. `editor/` — менеджер проектов (создать/открыть/сканировать/удалить проект, `.tprj` / `project.toml`, экспорт), окна: Hierarchy, Inspector, Project, Scene View, Game View, Console, Toolbar. Тёплая тёмная палитра Tellurium с пепельно-жёлтым и пепельно-оранжевым акцентами описана в §11 архитектуры.
3. **Разделение редактора и рантайма на этапе компиляции:** в `Cargo.toml` завести фичу `"editor"` (по умолчанию выключена). Весь код редактора (`editor/`, менеджер проектов, UI) компилируется только при `cargo build --features editor`. Без этой фичи собирается чистый рантайм (`tellurium_runtime.exe`) без редактора, без исходных ассетов и без инструментов разработки — это решает проблему «отсечения редактора» на этапе экспорта без ручного удаления кода.
4. Связь узлов и ECS: загрузка `.telsc` создаёт ECS-сущности и компоненты, transform узла — компонент `Transform`, скриптовые узлы получают `ScriptComponent`, инстансирование сцен (PackedScene).

**Критерий завершения шага 4:** запускается менеджер проектов (при `--features editor`), можно создать проект, собрать сцену в редакторе (иерархия узлов, инспекор с компонентами), нажать Play и увидеть работу сцены в Game View; без фичи `editor` собирается автономный рантайм.

## Шаг 5 — Экспорт и финальная сборка (Windows Build Pipeline)

**Модули:** `builder`, `templates/windows`  
**Ссылки в архитектуре:** §21 (Windows Build Pipeline), §21.1–21.5, §9.3–9.4 (кэш и выпечка .telpak)

**Что кодить:**
1. `builder/` — валидация проекта, компиляция Luau-скриптов в байт-код, упаковка `.telpak` (байт-код Luau, оптимизированные ресурсы из `.telcache`, сцены `.telsc`, конфигурация проекта), отсечение редактора и исходных ассетов, **формирование `.exe` из шаблона `tellurium_runtime.exe` без фичи `editor`** (`cargo build --release` без `--features editor`), копирование зависимостей (`d3d12.dll` или Vulkan-лоадер, Bullet .dll).
2. `templates/windows/` — предкомпилированный легковесный шаблон рантайма `tellurium_runtime.exe`, инициализирующий ядро (Rust) и загружающий C++ модуль через cxx мост, считывающий `.telpak`.

**Критерий завершения шага 5:** из редактора можно сделать экспорт в `.exe`, который запускается без редактора, без исходного кода и без инструментов разработки; cxx мост остаётся единственной границей Rust ↔ C++ в экспортированном билде.

## Шаг 6 — Полировка, отладка, горячая перезагрузка, безопасность

**Модули:** `diagnostics`, `safety` (+ доработка `scripting`, `assets`)  
**Ссылки в архитектуре:** §19 (Система горячей перезагрузки), §24 (Инструменты отладки и профилирования), §3.5 / §5 (Безопасность), §17 (Архитектурные вызовы), §20 (Плагины редактора)

**Что кодить:**
1. `diagnostics/` — профилировщик (Tracy) через cxx мост, сквозной таймлайн кадра (Rust + C++), метрики в Console: FPS, Frame Time, Активные сущности, Память Luau VM, Draw Calls, Время физики, Время ECS update.
2. `safety/` — безопасный Rust (блоки `unsafe` только в минимальных местах FFI-границ, обёрнутые в безопасные абстракции), проверка указателей на границе cxx, изоляция Luau (скрипт не может вызвать системный API напрямую). **Квоты CPU/памяти Luau и кастомный аллокатор уже настроены на Шаге 1 при инициализации VM.**
3. Горячая перезагрузка: отслеживание изменений `.luau`, `.png`, `.telsc` через watcher файловой системы, замена реализации функций скрипта с сохранением состояния (state preserving), горячая перезагрузка текстур и шейдеров на GPU без пересоздания конвейера.
4. Плагины редактора (Luau-плагины в изолированном состоянии, взаимодействие через Event Bus).

**Критерий завершения шага 6 (готовая первая версия):** работает профилировщик с метриками в реальном времени; изменение `.luau`-скрипта не перезапускает игру (state preserving hot reload); песочница Luau и квоты работают; движок проходит полный цикл кадра от ввода до present.

## Итоговая сводка шагов

| Шаг | Фокус | Модули | Видимый результат |
|-----|-------|--------|-------------------|
| 1 | Фундамент | `platform`, `core`, `scripting`, `runtime` | Окно + игровой цикл + скрипт меняет объект |
| 2 | Мостик и графика | `bridge`, `graphics-cpp` | Треугольник на экране, рендер через GPU |
| 3 | Ресурсы, физика, аудио, ввод | `assets`, `physics-cpp`, `audio-cpp`, `input` | Текстуры, падающие кубы, звук, действия ввода |
| 4 | Сцены и редактор | `editor`, `serialization` | Менеджер проектов, иерархия, инспекор, Play в редакторе |
| 5 | Экспорт | `builder`, `templates/windows` | `.exe` без редактора и исходных файлов |
| 6 | Полировка и отладка | `diagnostics`, `safety` | Профилировщик, метрики, hot reload, песочница |

После завершения всех шести шагов первая версия Tellurium Engine содержит всё, описанное в `ARCHITECTURE.ru.md` и графе `Tellurium/`: гибрид Rust + C++ через cxx, Luau-скрипты, ECS, Godot-подобную иерархию узлов, редактор, ассет-пайплайн (`.telmeta` / `.telcache` / `.telpak`), Windows-экспорт, отладку и безопасность.
